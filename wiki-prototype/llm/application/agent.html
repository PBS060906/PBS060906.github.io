Agent

Agent = 以 LLM 为大脑，循环执行“感知 → 规划 → 行动”的自主系统。

基本循环（ReAct）

任务输入→ 思考 Reason→ 行动 Act（调用工具）→ 观察 Observe（工具结果）→ 最终回答（任务完成）

观察结果回流至“思考”，如此循环，直到任务完成。

核心是让模型交替输出推理轨迹与工具调用，用观察结果修正后续决策。

工具调用

{
  "name": "get_weather",
  "description": "查询指定城市实时天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": {"type": "string", "description": "城市名"}
    },
    "required": ["city"]
  }
}

工具设计的黄金法则：名称自解释、描述写清适用与边界、参数少而精。

工具调用的标准协议

function calling 是模型与工具之间的标准协议：请求时用 JSON Schema 声明工具集，模型返回结构化的 name + arguments，而不是自由文本——这是 Agent 可靠执行的基石。

import json
from openai import OpenAI

client = OpenAI()

# 1) 请求：用 JSON Schema 声明工具集
resp = client.chat.completions.create(
    model="qwen-plus",
    messages=[{"role": "user", "content": "上海今天适合跑步吗？"}],
    tools=[{
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市实时天气",
            "parameters": {
                "type": "object",
                "properties": {"city": {"type": "string", "description": "城市名"}},
                "required": ["city"],
            },
        },
    }],
)

# 2) 响应：模型返回结构化调用，而非自然语言
tool_call = resp.choices[0].message.tool_calls[0]
print(tool_call.function.name)       # "get_weather"
print(tool_call.function.arguments)  # '{"city": "上海"}'

# 3) 执行工具，把结果以 role="tool" 拼回对话，模型据此作答
result = get_weather(**json.loads(tool_call.function.arguments))
messages.append(resp.choices[0].message)  # 保留模型的调用决策
messages.append({
    "role": "tool",
    "tool_call_id": tool_call.id,
    "content": json.dumps(result, ensure_ascii=False),
})

最小 Agent 循环

把「决策 → 解析 → 执行 → 观察」装进一个 while 循环，就是最小的可用 Agent（60 行内）：

import json
from openai import OpenAI

client = OpenAI()
MODEL = "qwen-plus"

def get_weather(city: str) -> str:
    # 示例工具：真实场景替换为 API 调用
    return json.dumps({"city": city, "temp": "22℃", "weather": "多云"},
                      ensure_ascii=False)

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市实时天气",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名"}},
            "required": ["city"],
        },
    },
}]
EXECUTORS = {"get_weather": get_weather}  # 工具名 → 可执行函数

def run_agent(question: str, max_steps: int = 8) -> str:
    messages = [
        {"role": "system", "content": "你是助手，需要时调用工具，完成后给出最终回答。"},
        {"role": "user", "content": question},
    ]
    for _ in range(max_steps):            # 步数上限，防止死循环与失控成本
        resp = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS)
        msg = resp.choices[0].message
        if not msg.tool_calls:            # 模型不再调用工具：任务完成
            return msg.content
        messages.append(msg)              # LLM 决策写入上下文
        for call in msg.tool_calls:       # 解析并执行每个 tool_call
            args = json.loads(call.function.arguments)
            result = EXECUTORS[call.function.name](**args)
            messages.append({             # 观察结果拼回 messages
                "role": "tool",
                "tool_call_id": call.id,
                "content": str(result),
            })
    return "达到步数上限，任务未完成。"

print(run_agent("上海和北京今天哪里更适合跑步？"))

RAG 与 Agent 的关系

RAG 是检索增强的单轮问答：固定流程先检索、后作答，检索由代码触发；Agent 则把检索降级为工具之一，由 LLM 自主决定何时检索、检索什么、检索后做什么。

维度RAGAgent
决策者代码写死的固定流程LLM 自主规划
检索时机每轮必检索一次按需，可多次、可跳过
检索后动作拼接上下文直接作答可改写查询、再检索、调用其他工具
适用场景知识库问答等单轮任务多步推理、开放性任务

实践上二者常组合为「Agent + RAG」：把检索器注册成一个工具，让模型自己判断是否需要查知识库。

规划模式

模式工作方式适用场景
ReAct想一步做一步，观察结果决定下一步探索型任务，每步依赖上一步的真实反馈
Plan-and-Execute先产出完整计划，再逐步执行（可中途重规划）步骤可预知、结构稳定的任务，总成本更低

经验法则：环境反馈多、路径不明就 ReAct；任务结构清晰就先规划再执行。

记忆机制

类型生命周期实现
短期记忆单次会话上下文窗口、消息历史
长期记忆跨会话向量库检索、结构化档案
工作记忆当前任务任务状态、TODO 列表

上下文工程

Agent 稳定性的关键是把正确的信息、在正确的时机、以正确的格式放进上下文：

  • 系统提示：角色 + 工具使用规范 + 停止条件；
  • 历史压缩：长对话滚动摘要，保留关键事实；
  • 错误注入防护：工具报错时回传可恢复的提示而非裸堆栈。

Agent 评测

  • 任务成功率：端到端完成率，核心指标；
  • 步数与成本：平均工具调用次数、token 消耗，衡量效率；
  • 工具调用准确率：选对工具、传对参数的比例，用于区分失败是"选错工具"还是"用错参数"。

评测方法：先构造可复现的评测集（任务 + 判定标准），固定随机性与模型版本，跑通基线后再做架构变更，用同一评测集对比。

Warning

没有评测就不要上多智能体：连单 Agent 的成功率与成本都没有基线，任何"升级"都无法证明有效。

安全与权限

  • 最小权限：Agent 只拿到完成任务所必需的工具与数据权限；
  • 工具白名单：生产环境禁用任意代码执行、任意文件读写等开放性工具；
  • 人工确认：删除数据、支付、外发邮件等高危操作必须人审后执行；
  • 沙箱隔离：文件与网络访问限制在指定目录与域名内，限制循环步数与预算。

多智能体协作

  • 编排者-执行者：主 Agent 拆解任务分发给子 Agent，汇总结果；
  • 流水线：按职能串行传递（写代码 → 审代码 → 测试）。

Warning

单 Agent + 好工具能解决 90% 的问题。多智能体引入的通信开销与失控风险，只有在任务可清晰拆分且并行收益大时才值得。
