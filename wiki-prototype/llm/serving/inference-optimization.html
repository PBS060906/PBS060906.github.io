推理优化

大模型推理的三大瓶颈：访存带宽、KV Cache 显存、请求调度。本页逐一拆解对应的优化技术：从 Prefill/Decode 两阶段的性能特征，到 KV Cache 压缩、PagedAttention、continuous batching、量化与投机解码。

性能指标：TTFT 与 TPOT

指标定义影响体验
TTFT（Time To First Token）请求发出到首个 Token 返回用户等多久开始看到字
TPOT（Time Per Output Token）首 Token 之后平均每个 Token 的间隔打字机效果的流畅度
Throughput单位时间整机完成的 Token 数服务成本
Goodput满足 SLO 约束的有效吞吐真实服务质量

TTFT 主要由 Prefill 决定，TPOT 主要由 Decode 决定，两者的优化手段因此分道扬镳。

请求到达→ Prefill：决定 TTFT→ Decode：决定 TPOT→ 响应完成

自回归生成的两阶段

Prefill 阶段：一次算完整个提示词→ Decode 阶段：逐 Token 自回归，每步读一遍 KV Cache
  • Prefill 是计算密集型：整段提示词并行过一遍网络，是大矩阵乘法，能吃满 GPU 算力；
  • Decode 是访存密集型：每生成一个词都要完整读一遍权重与 KV Cache，算力大量闲置，瓶颈在显存带宽——这是 Decode 必须靠 batching 摊薄成本的根本原因。

KV Cache

自回归生成时缓存历史 Key/Value，避免重复计算：

KV 显存 = 2 × 层数 × (头数 / GQA 分组数) × dhead × 序列长 × 批大小 × 字节数

以 7B 级模型、长上下文、大批并发为例，KV Cache 可达数十 GB，超过权重本身。压缩有三条路：

  1. 结构压缩：GQA/MLA 减少 KV 头数（见 Transformer）；
  2. 数值压缩：KV Cache 量化到 INT8/FP8；
  3. 复用：Prefix Caching——相同前缀（系统提示、Few-shot、文档）只算一次，跨请求共享；SGLang 的 RadixAttention 用基数树自动管理前缀复用。

PagedAttention

借鉴操作系统虚拟内存分页管理 KV Cache（vLLM 的核心）：

  • 将每条请求的 KV 序列切成固定大小的块（block，如 16 个 Token），逻辑连续、物理分散，按需分配；
  • 通过块表把逻辑位置映射到物理块，注意力核按块寻址；
  • 彻底消除「按最大长度预分配」造成的内部与外部碎片，显存利用率从 ~20% 提升到 90% 以上，等价于更大的有效 batch 与更高吞吐；
  • 前缀共享场景下多请求可映射到同一物理块（copy-on-write），与 Prefix Caching 天然契合。

一条请求的逻辑块到物理块的映射示意（逻辑连续、物理分散）：

逻辑块物理块状态
07满
13满
212半满（尾部按需增长）

Continuous Batching

传统静态 batch 必须等最长的序列完成才能换下一批，先完成的请求让 GPU 空转。连续批处理（iteration-level scheduling）在每个 Decode 步的边界动态插入/移除请求，完成的立即退出、新请求立即插入，吞吐提升数倍到数十倍，是所有现代推理框架的默认行为。

Chunked Prefill 与 PD 分离

  • Chunked Prefill：把超长提示词切成若干块，与 Decode 请求交错调度，避免一个长 Prefill 阻塞整批 Decode，改善 TPOT 抖动；
  • PD 分离：Prefill 计算密集、Decode 访存密集，特征迥异，干脆拆到不同实例部署（如 DistServe、Mooncake 的做法），各自独立扩缩容，SLO 更可控。

量化

权重占用是大头（7B 模型 FP16 约 14 GB），量化直接决定「塞得下多少、跑得多快」。两大 INT4 方案：

方案原理特点
GPTQ基于 Hessian 的逐列量化 + 误差补偿量化一列后把误差分摊到未量化列，INT4 质量损失较小
AWQ激活感知量化：y = (W diag(s))(diag(s)−1x)，按激活分布缩放通道缩放前后数学等价，显著通道免受量化伤害；INT4 下稳健，开源量化部署主流之一
精度相对显存典型质量损失适用
FP16/BF161×基线训练、高精度服务
FP8/INT80.5×几乎无损高吞吐在线服务
INT4（AWQ/GPTQ）0.25×轻微显存受限、单卡部署

Note

weight-only（AWQ/GPTQ）只量化权重、激活保持 FP16，省显存但带宽收益打折；weight-activation（FP8/INT8）连激活一起量化，能吃到完整的带宽红利，但对算子支持要求更高。

投机采样

用小模型快速起草、大模型一次验证：

  1. 草稿模型连续生成 k 个候选词；
  2. 目标模型并行验证这 k 个词（一次前向）；
  3. 从左到右逐词接受，第 t 个候选被接受的概率为：
Paccept(x) = min(1, p(x) / q(x))

其中 p 是目标模型、q 是草稿模型的概率；被拒时按修正分布重新采样一个词。数学上可证明输出分布与目标模型完全一致，单步可产出多个 Token。变体方向是「自我草稿」：EAGLE、Medusa 等用目标模型内部特征上的轻量头起草。注意：高并发大 batch 时 GPU 本已饱和，投机解码收益趋近于零，更适合低并发、低延迟场景。

from vllm import LLM, SamplingParams

# 用 AWQ 量化模型起步：显存减半、质量基本无损
llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct-AWQ",
    quantization="awq",
    gpu_memory_utilization=0.9,   # 预留显存比例
)

params = SamplingParams(temperature=0.7, max_tokens=512)
outputs = llm.generate(["用三句话解释 KV Cache 的作用"], params)
print(outputs[0].outputs[0].text)

Tip

先用 vLLM 起步建立基线，再针对 TTFT 或吞吐瓶颈引入专项优化。

实践要点

  1. 先分清瓶颈在 Prefill 还是 Decode：TTFT 差 → 长提示词场景上 Prefix Caching / chunked prefill；TPOT 差 → batching、带宽与量化；
  2. 量化是性价比最高的一步：线上 FP8/INT8 起步，显存紧张上 AWQ/GPTQ INT4，务必用业务数据回归评测质量；
  3. 系统提示与文档前缀尽量固定，吃满 Prefix Caching 的复用红利；
  4. 监控 TTFT/TPOT 的 P99 分位而非平均值，尾延迟才是用户的真实体验；
  5. 投机解码只投低并发、低延迟场景，大 batch 下不要指望它。
